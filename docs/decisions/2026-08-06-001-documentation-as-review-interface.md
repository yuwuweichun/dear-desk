# DD-ADR-20260806-001：将文档作为项目审核界面

## 状态

已接受，2026-08-06 12:04 CST。

## 背景

用户需要持续记录、阅读和审核 Dear Desk 的改动方案与项目架构，但不把直接阅读源码作为主要工作方式。仅在开发结束后补一份说明，无法支持实施前审批，也容易让方案、源码和架构文档逐渐分离。

## 决策

1. 每项独立任务先创建带日期和编号的 Markdown 记录。
2. 用户明确批准最终方案前，不修改业务源码、依赖或工程配置。
3. 实施完成后，在同一记录中回写实际改动、验证结果和文档同步情况。
4. 任务默认使用 Markdown；复杂架构和长篇导读使用符合 HTML 参考规范的本地 HTML。
5. Codex 完成实施后把任务标记为“待验收”，用户接受后才进入“已完成”。
6. 架构、产品范围和长期决策分别维护当前事实文档，不用历史任务记录代替当前状态。

## 原因

- Markdown 适合高频记录、文本差异和 Git 追踪。
- HTML 适合向不阅读源码的用户解释复杂结构和调用链。
- 先批准后实施让范围和技术判断在修改前可见。
- 完成后回写保证文档描述的是实际结果，而不是实施前设想。
- 历史记录与当前事实分开维护，能同时保留决策过程和准确现状。

## 影响

### 正面影响

- 每次源码变化都有可读原因、范围和验收依据。
- 用户可以在不阅读源码的情况下审核关键决策。
- 架构变化和产品范围变化被纳入完成门槛。
- Codex 实施时拥有明确边界，减少静默扩张。

### 成本

- 小任务也需要维护一份简短记录。
- 实施结束后需要核对计划与实际差异。
- HTML 架构文档需要额外的交互和视觉验证。

通过允许小任务简写 Markdown、只为复杂主题生成 HTML，控制额外成本。

## 替代方案

### 只使用 `AGENTS.md`

未采用。`AGENTS.md` 适合长期规则，不适合保存每项任务的具体讨论、批准和实施证据。

### 只在开发完成后写文档

未采用。用户无法在实施前审核范围和架构风险。

### 每项任务都生成 HTML

未采用。会增加重复内容和维护成本，也不利于查看方案文本差异。

## 后续约束

任何取消审批流程、改变状态含义或更换文档事实来源的工作，都需要新的决策记录替代本文。

### 2026-08-13 补充：Spec Kit 的从属边界

`DD-20260813-002` 批准引入 GitHub Spec Kit，作为复杂功能的规格拆解工具。`specs/<编号>-<功能名>/` 可以保存 `spec.md`、`plan.md`、`tasks.md` 和设计附件，但不取得独立批准权：

1. `docs/changes/` 仍是任务提出、用户批准、实施回写和验收状态的唯一入口。
2. `.specify/memory/constitution.md` 只映射 `AGENTS.md`、当前产品/架构文档和已接受 ADR，不成为新的上位事实来源。
3. `$speckit-implement` 只有在对应变更记录已批准且最终执行清单已经写入后才能运行。
4. 小型明确改动继续允许使用简短变更记录，不强制生成完整 Spec Kit 产物。

该补充没有取消或改变本文的审批状态机，只把新工具纳入既有制度。
