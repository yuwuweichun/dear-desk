# DD-ADR-20260831-001：采用 Luna 执行与 Sol 推理的双模型工作流

## 状态

已接受，2026-08-31 00:31 CST。用户明确要求直接建立该模式。

## 背景

Dear Desk 的日常工作包含大量代码读取、搜索、命令执行、局部修改和测试验证，也会偶尔遇到复杂架构、跨模块决策和疑难故障。始终使用同一高成本模型会让常规执行承担不必要的推理成本；把完整项目上下文反复交给另一个模型又会造成上下文污染和重复消耗。

## 决策

1. 项目新任务默认使用 `gpt-5.6-luna`、`medium` 推理强度执行。
2. 常规子代理也默认继承 Luna；不因存在多代理能力而自动并行或重复检查。
3. 新增只读自定义代理 `sol_reasoner`，固定使用 `gpt-5.6-sol`、`high` 推理强度。
4. 只有复杂架构设计、跨模块关键决策、局部排查后仍未解决的疑难 Bug 或确需深度权衡时，Luna 才调用 `sol_reasoner`。
5. 调用前由 Luna 生成约 1～3K Token 的 Task Packet，只包含当前目标、已确认事实、关键代码、核心约束、已尝试方案、待解决问题和期望输出。
6. Sol 只输出结构化分析、执行步骤、风险和验证标准；Luna 继续负责修改、测试、文档同步与最终交付。
7. Sol 的建议不取得独立批准权。若建议扩大当前批准范围，仍按 `AGENTS.md` 的任务审批流程处理。

## 原因

- Luna 适合清晰、重复、高频的执行任务，可承担大多数工具调用和实现工作。
- Sol 适合复杂专业推理，用在少量高价值决策点更符合质量与成本目标。
- Task Packet 限制跨模型上下文，减少无关历史、命令日志和完整代码库重复进入 Sol 上下文。
- 让 Luna 保持实现所有权，可避免分析代理与执行代理并发写入造成冲突。

## 影响

### 正面影响

- 常规任务默认走更轻量的执行路径。
- 复杂问题仍有明确、可审计的升级路径。
- Sol 输出直接面向 Luna 的实施和验证，不复制完整项目上下文。

### 成本与限制

- Luna 需要判断是否达到升级阈值，并维护高质量 Task Packet。
- 项目级模型配置只在项目受信任且新任务加载配置后生效，不会热切换已经运行的任务。
- Sol 的只读建议仍需 Luna 结合真实源码和批准边界复核。

## 替代方案

### 所有任务均使用 Sol

未采用。常规搜索、编辑和测试不需要持续使用最高推理成本。

### Luna 遇到问题时直接发送完整上下文

未采用。会重复传输无关项目历史和工具噪声，削弱问题聚焦。

### Sol 同时负责分析与修改

未采用。会分散实施所有权，并增加写入冲突与批准范围漂移风险。
