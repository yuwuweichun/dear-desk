# DD-ADR-20260806-002：本地数据事实与场景投影边界

## 状态

已接受，2026-08-06 13:21 CST。本文把编号 002 已批准并已实现的长期架构边界整理为当前决策记录。

## 背景

Dear Desk 需要让用户留下的文字和后续桌面痕迹在页面重新打开后仍然存在，同时使用 Three.js 表达空间关系。若 DOM、Zustand、Three.js 和 IndexedDB 都能各自成为业务状态来源，就会出现难以序列化、无法迁移和界面彼此不一致的问题。

首版已经明确不建立账号、服务端数据库或云同步，并要求数据模型与 Three.js 场景对象分离。

## 决策

1. 首版业务数据以当前浏览器 origin 下的 IndexedDB 为持久化事实来源，使用 Dexie 封装 schema、事务和查询。
2. Zustand 只协调当前页面内的可序列化应用状态和用户意图，不保存 Mesh、Texture、Material、Camera、Vector 或 DOM Event。
3. 领域类型与校验规则不依赖 React、Three.js 或 Dexie；UI 只通过 repository 接口访问持久化数据。
4. Three.js 场景是领域与应用状态的视觉投影，只读取可序列化值并发出应用 intent，不直接读写 IndexedDB。
5. 表单、编辑器、错误反馈和可访问交互继续使用 DOM；未经独立批准不增加第二个 WebGL 画布。
6. 数据库按已实现功能递增版本。v1 只包含 `dailyEntries`，不为贴纸、图片或台灯预建空表。
7. 清除站点数据、切换浏览器或更换设备不会自动迁移内容；在账号与云同步另行批准前，这属于产品边界。

## 原因

- IndexedDB 能保存结构化记录和后续图片 Blob，容量与事务能力比 `localStorage` 更适合产品方向。
- repository 隔离 Dexie 细节后，领域规则与 store 可以使用内存替身测试。
- Three.js 运行对象包含上下文和生命周期，写入 store 或数据库会破坏序列化、迁移和重建能力。
- DOM 对文字输入、焦点、键盘和错误提示更成熟，不需要把表单绘制到纹理。
- 按实际功能升级 schema 可以避免未验证的数据模型提前成为兼容负担。

## 影响

### 正面影响

- 页面重开可以从单一数据来源恢复记录。
- WebGL 不可用时仍能保留 DOM 日记与持久化链路。
- 场景可以被重建、替换或测试，而不会改变业务数据语义。
- 后续贴纸 schema 可以通过明确的 IndexedDB 版本迁移加入。

### 成本

- UI 不能直接操作 Dexie table，需要经过 store 与 repository。
- 拖动、动画等高频场景状态需要区分临时运行值和最终持久化值。
- 当前数据只在单一浏览器本地存在，用户需要理解清除站点数据的后果。

## 替代方案

### 使用 `localStorage`

未采用。简单文本可以保存，但事务、结构化查询、版本迁移和未来图片 Blob 支持较弱。

### 把 Three.js 对象放入 Zustand

未采用。运行对象不可可靠序列化，且会把 Canvas 生命周期泄漏到业务层。

### 把编辑器渲染到 WebGL 纹理

未采用。会降低文字输入、焦点、键盘和无障碍质量，并扩大 Canvas 的职责。

### 首版建立服务端同步

未采用。账号与云同步是已批准 MVP 的明确非目标，会显著扩大隐私、认证和运维范围。

## 后续约束

- 新增贴纸、图片或台灯数据时必须使用新的 IndexedDB 版本，并在任务记录中说明迁移、失败恢复和回退。
- scene 需要持久化的新交互只能提交领域值或 intent，不能保存 Three.js 实例。
- 引入服务端、跨设备同步、第二个 WebGL 画布或改变 repository 公共边界，都需要新的审批和决策记录替代或补充本文。
