02 · 工作方式

每项任务都经过同一条审核链路

新的独立任务先创建日期编号记录。Codex 可以读取源码、测试和配置来建立事实，但在用户批准前只修改方案文档。

01待确认读取事实并形成方案
02已批准锁定最终执行清单
03实施中按批准范围修改
04待验收展示结果和证据
05已完成由用户接受结果

这里的 意味着每次实现都应形成可运行、可验证的用户结果。实施中若出现会改变范围、主要交互、公共接口或数据结构的新问题，对应改动必须暂停并重新确认。

04 · 一致性

怎样防止文档与源码各说各话

每份任务记录都要保存分析时的源码基线，并在实施结束后补充真实文件、测试结果和方案偏差。涉及产品行为、架构边界或长期约束时，还要同步更新对应的当前事实文档。

  1. 先核对事实从真实源码、测试和运行行为建立现状，区分事实、预计改动、推断和待确认项。
  2. 再锁定范围用户批准后的执行清单是本次改动边界，实施中不能静默扩展。
  3. 最后回写结果把 Git 实际差异、验证证据和当前文档逐项同步，才能进入待验收。

让一份记录可以定位到具体版本； 则负责告诉阅读者项目现在是什么样子。

06 · 项目事实

当前应用已经形成记录与文字贴纸两条可运行链路

React 应用通过 Zustand 协调日记、本子和贴纸工作流，两个 Dexie repository 把当天记录与贴纸三类数据保存到 IndexedDB v2。WebGL 任意时刻只有一个活跃 Canvas：桌面阶段由 R3F 拥有，制作阶段切换给固定 commit 的 Sticker Forge。

贴纸链路是“未保存日记草稿 -> Sticker Forge 制作与 peel 预览 -> 透明 PNG 快照 -> 桌垫放置 -> 三表事务 -> R3F 纹理投影 -> 移动/15° 旋转/删除 -> 刷新恢复”。图片贴纸、过去日期和台灯仍未实现，不能从已批准产品范围反推为源码事实。

src/main.tsx组合 repository、store 与 React 根
src/state/app-store.ts本子状态机、贴纸工作流与异步状态
src/persistence/IndexedDB v2、日记仓储与贴纸三表事务
src/integrations/sticker-forge.ts固定官方 bundle、flat 快照与销毁生命周期
src/features/stickers/制作宿主、材质控件与桌面命令
src/scene/R3F Canvas、本子转场、贴纸放置与 PNG 投影
