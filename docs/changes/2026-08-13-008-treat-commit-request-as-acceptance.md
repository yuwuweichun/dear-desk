## 1. 给阅读者的结论

建议在项目协作规则中增加“提交即预先验收授权”：当用户在一个变更任务中明确要求 Codex 创建提交时，只要实施未超出已批准范围且全部必要验证通过，Codex 应先把任务记录更新为“已完成”，再把源码、文档和验收状态放入同一个提交。这样不会在实现提交后仅为回写“已完成”再产生第二个提交。

该规则不允许 Codex 在验证失败、范围发生实质变化或提交未成功时虚报完成，也不把普通的提交讨论、提交信息建议或询问是否提交解释为授权。

## 2. 用户需求

- 用户原始要求：“下次指明提交的话，就是已验收，这个规则写入项目AGENTS.md”。
- Codex 解释：用户对当前任务明确发出“提交”“做一次提交”等创建提交指令时，同时预先接受在批准范围内且验证通过的最终结果；Codex 应在提交前完成验收回写，使一个提交包含完整任务闭环。
- 验收意图：以后明确要求提交的任务不再因为提交后补记验收而产生第二次文档提交。

## 4. 目标与非目标

### 4.1 目标

- 在根 `AGENTS.md` 明确定义“明确要求创建提交”同时构成条件式预先验收授权。
- 要求验证通过且没有超出批准范围时，在提交前将任务记录更新为“已完成”。
- 修正 `AGENTS.md` 中与新规则冲突的无条件“待验收”要求。
- 明确不满足条件时仍停留在相应状态，不得虚报完成或强行提交。

### 4.2 非目标

- 不改变任务方案审批要求。
- 不把“要不要提交”“提交信息怎么写”等讨论视为提交授权。
- 不授权自动 push、创建 PR、amend、rebase 或修改历史。
- 不修改业务源码、工程配置、产品范围或持久化数据。
- 不处理无关的 `DD-20260813-007` 任务。

## 5. 方案说明

在 `AGENTS.md` 的“审批状态”增加一条例外规则：用户明确要求为本任务创建提交时，该指令同时构成对“批准范围内、必要验证通过、无未批准偏差”的最终结果的预先验收；Codex 在提交前完成实施和验证回写，将状态直接更新为“已完成”，再创建单一提交。

同步修改“文档与源码一致性门槛”第 8 项，使默认路径仍为“待验收”，明确提交路径则按上述条件进入“已完成”。在“Git 约束”补充提交必须包含该任务完整的源码、文档、验证和验收状态，防止再次出现提交后补写状态。

### 6.2 上下游与跨模块影响
