## 6. 每项任务的状态流转

```text
已提出
  -> 待确认
  -> 已批准
  -> 实施中
  -> 待验收
  -> 已完成

可选终态：已拒绝 / 已取消 / 已替代
```

状态规则：

| 状态 | 允许的动作 | 禁止的动作 |
| --- | --- | --- |
| 待确认 | 读取源码、运行只读检查、编写和修改方案文档 | 修改业务源码、安装依赖、迁移数据 |
| 已批准 | 将批准内容整理为最终执行清单 | 扩大未批准范围 |
| 实施中 | 修改清单内源码、测试和相关文档 | 静默改变关键架构决策 |
| 待验收 | 展示真实结果、测试证据和差异 | 把计划描述当作实施事实 |
| 已完成 | 维护当前事实文档、修正文档错误 | 继续追加未记录的新功能 |

以下用户表达可视为批准：明确回复“批准”“按此执行”“可以开始”或明确批准某个方案版本。含糊反馈和继续讨论不视为批准。

若实施中发现会改变范围、数据结构、主要交互或架构的新问题，应暂停对应改动，把问题写入“方案偏差与新增决策”，重新等待确认。普通编译错误、局部实现细节和不改变批准方案的修正不需要重复审批。

## 7. Markdown 任务记录固定框架

所有任务记录使用相同一级章节。小任务可以简写，但不能删除章节；不适用时应写明“不适用”及原因。

1. **文档信息**：编号、日期、状态、类型、源码基线、关联提交。
2. **给阅读者的结论**：不用源码知识也能理解的一段摘要。
3. **用户需求**：保留目标、限制和验收意图。
4. **当前源码事实**：说明目前实际行为，并列出证据路径或测试。
5. **目标与非目标**：明确本次边界。
6. **方案说明**：解释用户体验、系统行为和选择理由。
7. **预计改动与影响评估**：文件、模块、数据结构、上下游和兼容性。
8. **风险、边界与回退**：发生条件、影响、缓解和撤销办法。
9. **验证与验收**：自动测试、浏览器场景、持久化和视觉检查。
10. **待确认项与决策**：仅列出真正影响方案的问题。
11. **最终批准方案**：记录批准版本、时间和执行清单。
12. **实施记录**：实际改动、方案偏差和关联源码。
13. **验证结果**：真实命令、结果、截图或已知缺口。
14. **文档同步检查**：列出同步更新的产品、架构和决策文档。
15. **审阅记录**：按时间追加用户反馈、决策和状态变化。

## 8. Markdown 与 HTML 的职责边界

### 8.1 默认使用 Markdown 的内容

- 每次任务的变更记录。
- MVP 范围、验收清单和简短决策记录。
- 尚在频繁讨论、需要清楚查看文本差异的方案。

原因：Markdown 更容易审阅差异、维护历史、与源码提交绑定，也适合每个任务都生成。

### 8.2 应使用 HTML 的内容

- 项目总览和系统架构。
- 涉及三个以上模块的数据流、时序或状态变化。
- 需要搜索、目录、术语解释和源码地图的长篇导读。
- 用户明确要求用可浏览页面展示的方案或审核报告。

HTML 生成必须遵循 `/Users/song/Desktop/docs-html/AGENTS.md`。它不是把 Markdown 套一层样式，而是面向不读源码的读者重新组织信息。每篇新增或实质更新的 HTML 都必须用 ego-browser 验证桌面和移动端阅读体验。

### 8.3 推荐默认值

- 每项任务：必有一份 Markdown 记录。
- 架构变化：同时更新对应 HTML 当前事实文档。
- 小型局部改动：不强制额外生成独立 HTML。
- `docs/index.html`：作为文档入口，展示当前架构文档和最近任务状态。

这样既保证“每次任务有记录”，又避免为一个文字修正维护一整套重复 HTML。

## 9. 文档与源码一致性机制

一致性不能只依赖“记得更新”，建议设置以下硬性门槛：

1. 每份任务记录保存开始分析时的 Git commit，完成时保存实现 commit。
2. “当前源码事实”必须引用真实相对路径、关键符号或测试，不允许只写概念描述。
3. 实施完成后将“预计改动”与 Git 实际差异逐项核对，并填写“实施记录”。
4. 修改主链路、状态所有权、持久化模型或公共接口时，必须同步更新 `docs/architecture/`。
5. 修改产品行为或验收边界时，必须同步更新 `docs/product/mvp.md`。
6. 新增长期架构约束时，必须新增或更新 `docs/decisions/`。
7. 验证脚本检查文档引用的源码路径是否存在、任务元数据是否齐全、是否仍有未处理的占位内容。
8. Codex 的最终交付必须列出“源码改了什么、文档改了什么、如何验证、还有什么未完成”。
9. 未完成文档回写的源码改动不能标记为“已完成”。

文档的事实优先级建议定义为：

```text
可运行源码与自动测试
  -> 已批准且完成回写的任务记录
  -> 当前架构文档
  -> 产品与设计说明
  -> 旧记录和合理推断
```

如果文档与源码冲突，不能默默选择其一。Codex 应在新任务记录中指出冲突，并根据用户确认修正文档、源码或两者。

## 10. 每次交给 Codex 任务后的实际流程

1. Codex 创建新的日期编号记录，状态设为“待确认”。
2. Codex 只读检查相关源码、测试、配置和现有文档。
3. Codex填写当前事实、方案、影响、风险、验收和待确认项。
4. Codex 把文档路径和最重要的决策摘要交给用户审阅。
5. 用户提出调整，Codex 更新同一份记录，并追加审阅记录。
6. 用户明确批准后，Codex 写入“最终批准方案”，状态改为“已批准”。
7. Codex 按清单实施，同时更新任务状态和必要的当前事实文档。
8. Codex 完成测试与浏览器验证，填写真实结果，状态改为“待验收”。
9. 用户验收或明确接受后，状态改为“已完成”。

紧急微小修复也保留同一流程，但记录可以很短。若用户在任务中明确说“无需方案审批，直接执行”，则可以在同一轮中把记录标为“用户授权直接执行”，仍需在完成后回写实施和验证结果。

## 12. 风险与回退

| 风险 | 发生条件 | 缓解方式 |
| --- | --- | --- |
| 每个小任务文档成本过高 | 所有任务都要求长篇 HTML | 默认用固定但可简写的 Markdown |
| 文档描述的是理想而非源码 | 架构文档早于实现且未标状态 | 严格区分预计架构与当前事实 |
| 实施结束忘记更新文档 | 完成标准只检查测试 | 将文档回写设为质量门槛 |
| 方案讨论无限延长 | 待确认项没有清晰决策 | 每次只保留影响实施的决策点 |
| 文档引用逐渐失效 | 文件移动或符号重命名 | 自动检查路径，人工核对关键符号 |
| HTML 与 Markdown 重复维护 | 同一内容存在两个事实来源 | 任务记录用 Markdown，架构导读用 HTML |

本次只有新增文档，可以直接删除本文回退，不影响任何源码或项目数据。
