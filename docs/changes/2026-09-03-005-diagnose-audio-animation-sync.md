## 1. 给阅读者的结论

音频晚于动画最可能不是“音频文件太大导致加载卡顿”这一单一原因，而是两个时序问题叠加：音效在对应动作首次发生时才创建 `HTMLAudioElement`，首次播放可能等待资源请求/解码；同时，动画由 Three.js 的每帧循环推进，音效由 React 状态更新后的 `useEffect` 触发，二者没有共享一个精确的媒体时钟。

Three.js 场景存在真实的渲染压力来源：抗锯齿、最高 1.5 DPR、PCF 阴影、多个程序化 PBR 纹理，以及翻书时每帧更新动态几何顶点法线和实例矩阵。但当前代码已对桌面、桌垫和本子设置资源预算，不能仅凭“场景复杂”断言它就是根因。应先测量动画期间的帧时间、主线程长任务、音频 `play()` 到 `playing` 的延迟，再决定是优先预热音频、降低场景成本，还是调整触发时机。

最小有效修复方向是：页面初始化后在首次用户手势中预加载/解码五条音效，并记录实际 `play()`/`playing` 延迟；若仍有明显偏差，再把音频触发从 React effect 前移到成功动作的统一状态入口，或按实测延迟做补偿。不要先引入 Web Audio 或重写整个 Three.js 场景。

## 2. 用户需求

- 用户观察到有时音频晚于动画。
- 用户希望知道是否因为音频加载卡顿、是否因为整体 Three.js 渲染压力，以及如何优化或解决。
- 本次解释当前根因与建议，不默认授权修改业务源码、依赖或架构。

## 3. 当前源码事实

- `src/audio/audio-controller.ts` 使用原生 `HTMLAudioElement`。每种音效第一次播放时才由 `new Audio(source)` 创建播放器，并设置 `preload = 'auto'`；控制器没有在页面空闲期显式预加载或等待 `canplaythrough`/解码完成。
- `src/audio/AudioRuntime.tsx` 通过 `useEffect` 观察 `NotebookPhase`、`JournalTurnPhase` 和 `PastTracesPhase` 的状态边沿后调用 `controller.playSfx(...)`。因此触发点是 React 提交后的 effect，不是鼠标事件本身，也不是动画帧本身。
- `src/scene/NotebookObject.tsx` 在 `useFrame` 中使用 `performance.now()` 推进开合动画；`src/scene/DeskScene.tsx` 的 `CameraRig` 也在 `useFrame` 中使用同一类时间推进相机动画。动画时长依据视口和 reduced-motion 动态变化。
- 关本音效由 `AudioRuntime` 按动画时长减去音频时长计算延迟：标准视口约 `424ms`，紧凑视口约 `24ms`。这是假定 `play()` 近似立即开始；若媒体首次播放或主线程繁忙，该假定不成立。
- `src/audio/audio-controller.ts` 对播放 Promise 只捕获失败，不记录 `play()` 调用到实际 `playing` 事件的延迟，因此当前自动测试无法证明音画同步。
- `src/scene/DeskScene.tsx` 配置了 `dpr: [1, 1.5]`、WebGL antialias、`shadows: true`、PCF 阴影和一盏 `1536 × 1536` 阴影贴图方向光。
- `src/scene/NotebookObject.tsx` 的模型更新会调用 `setOpenProgress`；`src/scene/models/create-notebook-model.ts` 在该过程中更新连续壳体顶点、重算顶点法线/包围体，并更新 5 个实例化过渡页的矩阵。这是翻书期间的额外 CPU/GPU 工作。
- `src/scene/models/model-specs.ts` 将固定模型预算设为最多 45 draw calls、80,000 triangles、16 textures；`model-factories.test.ts` 验证桌面、桌垫、本子合计处于预算内。该预算是上限约束，不是实际设备帧率证明。
- `public/audio/` 的五条音效文件约为 8–27 KB；文件体积本身较小，但网络取回、浏览器解码和首次媒体启动仍可能产生可见延迟。
- 当前工作区有既有未提交修改，涉及 AGENTS、产品/架构文档、场景模型与测试；本调研未修改这些文件。

### 合理推断

- 首次触发某一音效时，媒体尚未完成加载/解码，是“偶发晚于动画”的高概率原因，尤其是刷新页面后的第一次开本、翻页或抽屉动作。
- 若延迟只在低端设备、移动设备、高 DPR 或开启房间背景时出现，则主线程长任务或渲染帧时间过长的可能性升高。
- 若音频每次都稳定晚约同一个毫秒数，即使帧率正常，更像是 `useEffect` 触发点、音频启动延迟或关本固定补偿值不准确，而不是整体渲染性能。

## 4. 目标与非目标

### 4.1 目标

- 区分媒体加载/解码延迟、React 状态触发延迟和 Three.js 帧率压力。
- 给出按收益排序的低风险优化路径。
- 保持音效失败不阻断本子、翻页和抽屉动作。

### 4.2 非目标

- 本次不直接重写音频系统。
- 不在没有测量数据前关闭所有阴影、降低全部模型精度或引入新的音频依赖。
- 不把音频运行对象放入 Zustand、IndexedDB 或 Three.js 场景状态。

## 5. 方案说明

建议分三层处理：

1. **先测量**：在开发诊断模式记录动作意图时间、状态边沿时间、`play()` 调用时间、`playing` 事件时间，以及每帧耗时；同时用浏览器 Performance/Long Tasks 查看动画期间是否有超过 50ms 的主线程任务。分别测试首次播放和已预热播放、房间背景开关、DPR 1/1.5、桌面和移动视口。
2. **先修音频冷启动**：在页面加载动画期间创建五条音效并异步 `load()`；首次合格用户手势只负责完成浏览器允许的播放解锁。不要让音频准备阻塞首屏；播放动作时复用已准备好的资源。由于音效文件很小，这通常是最小且收益最高的修复。
3. **再处理触发和渲染**：如果预热后仍晚，统一从成功动作的状态提交入口触发，减少 React effect 的一拍延迟；如果帧时间确实超预算，再按测量结果降低 DPR、关闭非关键阴影接收/投射或减少翻书动态几何更新。每次只改一个变量并复测。

## 6. 预计改动与影响评估

用户已确认先实施音频预加载；精准音画同步的 AudioBuffer/AudioContext 方案只有在预加载后仍有不同步证据时才进入后续任务。实际范围为：

- `src/audio/audio-controller.ts`：增加 `preloadSfx()`，一次创建五个播放器并调用 `load()`，不主动播放。
- `src/app/App.tsx`：页面级控制器创建时同步调用 `preloadSfx()`；音频准备不阻塞场景 Loading。
- `src/audio/*.test*`：覆盖五个播放器创建、加载且不播放。
- 未修改 `AudioRuntime`、Three.js 时钟或模型；若预加载后仍不同步，再单独评估统一动作开始时间或 AudioBuffer/AudioContext。

### 6.1 核心数据结构变化

当前无变化。推荐后续只增加运行时的 `ready/loading/failed` 状态，不持久化音频对象或解码缓冲。

### 6.2 上下游与跨模块影响

音频控制器受浏览器媒体生命周期影响；Three.js 只继续负责视觉投影。预热需要用户手势以满足自动播放策略，且失败仍必须静默降级。

## 7. 风险、边界与回退

| 风险 | 发生条件 | 影响 | 缓解与回退 |
| --- | --- | --- | --- |
| 预热仍被浏览器策略限制 | 页面尚未获得用户手势 | 音效仍可能首次延迟 | 在首次点击/触摸中准备；失败继续使用现有播放路径 |
| 预加载占用网络或内存 | 设备资源紧张 | 首屏请求增加 | 仅预热五条小音效；必要时只准备当前工作流音效 |
| 误把帧率问题当音频问题 | 未区分 `play()` 与 `playing` | 改动无收益 | 先记录时间戳和帧时间再实施 |
| 降低渲染质量影响视觉 | 直接全局关闭阴影/DPR | 产品观感下降 | 只在实测低帧率设备上做自适应或单项降级 |
